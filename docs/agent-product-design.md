## 2. 产品概述

### 2.1 产品定位

智能导购 Agent 是黑马点评现有商户、优惠券、博客和用户体系之上的自然语言入口。用户通过一句话描述需求，Agent 负责理解条件、查询真实业务数据、组合筛选结果，并以商户卡片和推荐理由的形式给出可执行的消费建议。

产品不是通用聊天机器人，也不替代现有商户列表、商户详情和优惠券页面，而是作为更自然的任务入口，降低用户筛选成本。

### 2.2 核心价值

- 对用户：从“填写筛选条件”升级为“描述需求”，更快找到合适的店。
- 对平台：提高商户详情访问、博客阅读、优惠券领取和复购转化。
- 对工程能力：验证大模型工具调用、业务数据校验、会话记忆、流式响应和降级方案。

### 2.3 核心原则

1. **真实数据优先**：价格、库存、营业时间、距离和优惠券状态必须由业务服务校验。
2. **模型负责理解，代码负责决策**：模型负责意图识别和工具编排，业务代码负责查询、过滤、排序和权限。
3. **只读先行**：MVP 只支持查询和推荐，不直接执行购买、订阅等有副作用操作。
4. **可解释可降级**：推荐结果需要说明依据；模型不可用时仍能返回普通搜索结果。
5. **渐进式个性化**：先使用明确表达和高置信行为构建偏好，不依据一次对话永久修改用户画像。

## 3. 产品目标与非目标

### 3.1 MVP 目标

- 用户可以用自然语言搜索商户。
- Agent 能识别位置、品类、预算、距离、营业时间和消费场景。
- Agent 能结合优惠券、商户详情、博客或评论生成推荐。
- Agent 支持连续追问和筛选条件修改。
- 返回结构化商户卡片，可跳转现有商户详情页。
- 会话保存于 Redis，支持基础历史上下文。
- 模型或检索异常时自动降级到结构化商户搜索。
- 记录完整的请求、工具调用和耗时指标。

### 3.2 MVP 不包含

- 自动抢购优惠券、取消订单或修改用户数据。
- 商家运营助手和平台运维助手。
- 全量向量数据库和复杂推荐模型训练。
- 自动发布博客、营销文案或商户信息。
- 跨平台地图导航和第三方支付。

## 4. 目标用户与典型场景

### 4.1 目标用户

- 希望快速找店、但不愿填写复杂筛选条件的普通用户。
- 有明确预算、距离、场景或时间要求的用户。
- 已登录且有浏览、收藏、关注或消费记录的回访用户。

### 4.2 典型场景

#### 场景 A：自然语言找店

> 拱墅区有没有适合约会、人均 100 元以内的餐厅？

系统提取区域、品类、场景和预算，返回符合条件的商户列表。

#### 场景 B：附近和时间约束

> 找距离我 3 公里内、晚上 9 点还营业的火锅店。

系统结合当前定位、Redis GEO、营业时间和商户类型进行筛选。

#### 场景 C：优惠券导购

> 哪家店现在有比较划算的代金券？

系统查询有效优惠券、售价、面值、规则和库存，并解释优惠力度。

#### 场景 D：连续追问

```text
用户：推荐几家适合朋友聚餐的店
Agent：找到 5 家……
用户：预算控制在每人 100 元以内
Agent：筛选后剩下 2 家……
用户：哪家离地铁近？
Agent：推荐 A 店，距离地铁口约 500 米……
```

#### 场景 E：结果比较

> 这两家哪家更适合第一次约会？

系统根据价格、评分、营业时间、内容关键词、距离和优惠券做对比，并明确说明依据和数据时间。

## 5. 用户流程

### 5.1 主流程

```text
进入智能导购页
  -> 输入自然语言需求
  -> Agent 解析意图和约束
  -> 调用商户/位置/优惠券/内容工具
  -> 业务层过滤、排序和校验
  -> Agent 生成推荐说明
  -> 展示文本、商户卡片和优惠券卡片
  -> 用户查看详情或继续追问
```

### 5.2 无结果流程

1. Agent 说明没有完全匹配的结果。
2. 给出放宽建议，例如扩大距离、提高预算或取消营业时间限制。
3. 用户确认后重新查询。

示例：

> 暂时没有同时满足“2 公里内、100 元以内、评分 4.5 以上”的商户。要不要扩大到 5 公里，或将预算提高到 150 元？

### 5.3 异常降级流程

```text
模型超时/不可用
  -> 提取关键词和简单约束
  -> 调用普通商户搜索
  -> 返回标准列表
  -> 提示智能推荐暂时不可用
```

## 6. 功能需求

### 6.1 对话入口

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F-01 | 用户可以输入自然语言问题 | P0 |
| F-02 | 支持发送、停止生成和重新生成 | P0 |
| F-03 | 支持快捷问题，如“附近有什么好吃的” | P1 |
| F-04 | 支持 SSE 流式展示回答 | P1 |
| F-05 | 支持未登录用户进行基础商户查询 | P1 |
| F-06 | 登录后绑定会话和用户偏好 | P1 |

### 6.2 意图和条件理解

MVP 至少支持以下字段：

```json
{
  "intent": "SHOP_RECOMMENDATION",
  "keyword": "日料",
  "location": "拱墅区",
  "latitude": 30.31,
  "longitude": 120.15,
  "radiusMeter": 3000,
  "budgetMax": 100,
  "minScore": 4.5,
  "openAt": "21:00",
  "scene": "约会",
  "needVoucher": true
}
```

要求：

- 无法确定的字段不猜测，保留为空并继续查询。
- 预算、距离和时间必须转换为明确的结构化值。
- 用户后续修改条件时，只更新相关字段。
- 对“附近”“现在”“便宜”“高评分”等模糊表达使用可解释的默认规则。

### 6.3 商户搜索和推荐

支持以下过滤条件：

- 商户名称或关键词。
- 商户类型。
- 地理位置和半径。
- 人均价格上限或价格区间。
- 最低评分。
- 指定时间是否营业。
- 是否存在有效优惠券。
- 场景标签或内容相关性。

推荐结果必须包含：

- 商户 ID、名称、类型和地址。
- 距离、评分、人均价格和营业状态。
- 有效优惠券摘要。
- 推荐理由。
- 数据更新时间或“实时查询”标识。

### 6.4 商户详情和内容增强

用户点击卡片后复用现有商户详情页面。Agent 可以查询与商户关联的博客和评论，用于回答：

- 为什么适合约会或聚餐？
- 用户常提到哪些菜品？
- 环境、服务和拍照体验如何？

内容只能作为推荐解释和相关性依据，不能覆盖实时价格、库存、营业时间等结构化字段。

### 6.5 优惠券查询

优惠券卡片至少展示：

- 优惠券名称、售价和面值。
- 使用规则和有效期。
- 剩余库存或库存状态。
- 是否需要秒杀。
- 当前用户是否满足领取条件。
- 查看详情或进入现有优惠券页面的入口。

MVP 只查询，不执行领取、秒杀和订阅。后续开放操作时必须增加确认弹窗、幂等号、权限校验和审计日志。

### 6.6 会话管理

- 新建会话时生成 `conversationId`。
- Redis 保存最近若干轮消息和筛选条件。
- 支持继续上一次会话。
- 支持删除会话和清空上下文。
- 对历史内容进行摘要，避免上下文无限增长。

建议 Key：

```text
agent:conversation:{conversationId}
agent:conversation:user:{userId}
```

## 7. 工具设计

Agent 工具必须是显式注册的业务能力，不允许模型直接访问数据库、Redis 或 Spring Service Bean。

### 7.1 MVP 工具清单

| 工具 | 作用 | 类型 |
| --- | --- | --- |
| `searchShops` | 按结构化条件搜索商户 | 只读 |
| `searchNearbyShops` | 查询指定位置附近商户 | 只读 |
| `getShopDetail` | 查询商户详情 | 只读 |
| `listShopVouchers` | 查询商户有效优惠券 | 只读 |
| `getShopContent` | 查询商户博客、评论和内容摘要 | 只读 |
| `getUserPreference` | 查询当前用户已确认偏好 | 只读 |
| `subscribeVoucher` | 订阅优惠券提醒 | 二期，需确认 |

### 7.2 工具接口约束

```java
public interface AgentTool<I, O> {

    String name();

    String description();

    Class<I> inputType();

    O execute(I input, AgentContext context);
}
```

每个工具需要定义：

- 输入字段和校验规则。
- 最大返回条数。
- 超时和重试策略。
- 是否允许未登录调用。
- 是否涉及用户隐私或副作用。
- 可观测指标和错误码。

## 8. 推荐排序策略

基础排序由代码完成，大模型只负责解释结果。MVP 可使用以下权重：

```text
推荐分 =
  距离匹配分 * 0.25
+ 价格匹配分 * 0.20
+ 评分分 * 0.20
+ 营业时间匹配分 * 0.15
+ 优惠券分 * 0.10
+ 内容相关性分 * 0.10
```

排序规则：

- 硬约束优先于软排序，例如已打烊商户不能因为评分高而排在营业商户之前。
- 用户明确给出的条件优先级高于默认权重。
- 没有价格、评分或营业时间数据时，不得补造，降级为“信息缺失”并降低排序分。
- 推荐理由引用实际字段，例如“距离 850 米、人均约 80 元、有有效代金券”。

## 10. API 设计

### 10.1 对话接口

```text
POST /agent/chat
POST /agent/chat/stream
GET  /agent/conversations
GET  /agent/conversations/{conversationId}/messages
DELETE /agent/conversations/{conversationId}
```

请求示例：

```json
{
  "conversationId": "c_10001",
  "message": "拱墅区人均100以内适合约会的餐厅",
  "stream": true
}
```

响应示例：

```json
{
  "conversationId": "c_10001",
  "answer": "我为你找到 3 家比较合适的餐厅。",
  "cards": [
    {
      "type": "shop",
      "shopId": 1,
      "name": "103茶餐厅",
      "distanceMeter": 850,
      "score": 4.5,
      "averagePrice": 80,
      "openNow": true,
      "reason": "价格符合预算，晚间营业，距离较近"
    }
  ],
  "filters": {
    "location": "拱墅区",
    "budgetMax": 100,
    "scene": "约会"
  },
  "pendingAction": null,
  "traceId": "trace-xxx"
}
```

### 10.2 错误码建议

| 错误码 | 含义 |
| --- | --- |
| `AGENT_REQUEST_INVALID` | 请求内容为空或超过长度限制 |
| `AGENT_RATE_LIMITED` | 超出 Agent 访问频率 |
| `AGENT_MODEL_TIMEOUT` | 模型调用超时 |
| `AGENT_TOOL_TIMEOUT` | 业务工具调用超时 |
| `AGENT_NO_RESULT` | 没有满足条件的商户 |
| `AGENT_FALLBACK` | 已降级到普通搜索 |
| `AGENT_UNAUTHORIZED` | 用户无权查看目标数据 |

可先在核心服务中以独立包实现：

```text
hmdp-core-service/src/main/java/org/javaup/agent
├── controller
├── application
├── model
├── tool
├── memory
├── ranking
├── policy
└── observability
```

稳定后再抽为独立 `hmdp-agent` Maven 模块。

架构分层：

```text
Vue3 对话页
  -> AgentChatController
  -> AgentOrchestrator
  -> LlmClient + ToolRegistry
  -> 现有 Shop/Voucher/Blog/User Service
  -> MySQL / Redis / Kafka
```

建议模型客户端优先使用 OpenAI 兼容协议，以便切换云模型或国内模型。模型配置使用环境变量，不把密钥提交到仓库。

## 13. 安全、权限与合规

- 用户私有数据必须使用当前登录用户身份进行二次校验。
- 用户评论和博客属于不可信输入，不能改变系统指令或工具权限。
- 对工具输入做 Bean Validation，限制条数、半径、价格和时间范围。
- 设置最大工具调用次数、最大上下文长度和单次响应超时。
- 记录模型输入输出摘要，敏感手机号、Token 和个人信息脱敏。
- 购买、订阅、取消订单等操作必须先确认，MVP 不开放。
- 不允许 Agent 绕过现有限流、秒杀令牌、库存扣减和订单链路。

## 14. 非功能需求

### 14.1 性能

- 普通查询首屏响应目标不超过 2 秒，不含模型流式生成尾延迟。
- SSE 首 Token 目标不超过 3 秒。
- 单次请求最多调用 5 个工具，最多返回 10 个商户。
- 单个会话上下文限制在可控 Token 范围内。

### 14.2 稳定性

- 模型超时、限流或服务异常时自动降级。
- 工具调用支持超时、有限重试和熔断。
- 推荐结果必须标识实时数据查询失败的字段。
- Agent 故障不能影响现有商户和优惠券接口。

### 14.3 可观测性

每次请求至少记录：

```text
traceId
userId
conversationId
intent
modelName
toolName
toolLatency
toolError
inputTokens
outputTokens
firstTokenLatency
totalLatency
fallback
```

建议指标：

```text
agent_request_total
agent_request_latency
agent_tool_call_total
agent_tool_latency
agent_tool_error_total
agent_model_token_usage
agent_fallback_total
agent_no_result_total
```

## 15. 数据检索演进

### 阶段一：结构化查询

直接复用 MySQL、MyBatis-Plus 和 Redis GEO，支持类型、距离、价格、评分、营业时间和优惠券状态过滤。

### 阶段二：关键词和标签

对博客、评论和商户字段增加关键词检索，沉淀“约会、聚餐、适合拍照、亲子、夜宵、安静、性价比高”等场景标签。

### 阶段三：向量检索

对商户介绍、博客和评论进行向量化，用于复杂语义召回。向量结果必须回到结构化业务数据做实时校验，不能作为库存、价格和有效期的最终来源。

## 16. 分阶段路线图

### Phase 1：只读导购 MVP

- `/agent/chat` 和 `/agent/chat/stream`。
- 商户搜索、附近商户、详情、优惠券和内容工具。
- Redis 会话记忆。
- Vue3 对话页和商户卡片。
- 基础排序、日志、指标和降级。

### Phase 2：推荐质量增强

- 博客和评论关键词检索。
- 场景标签和内容相关性排序。
- 连续追问和筛选条件可视化。
- 用户明确偏好记录。
- 无结果改写和推荐对比。

### Phase 3：低风险动作

- 优惠券订阅和开抢提醒。
- 操作确认弹窗。
- 幂等操作号和审计日志。
- 复用现有限流、令牌和消息链路。

### Phase 4：评测和优化

- 建立真实问题评测集。
- 评估意图识别、工具参数、结果相关性和幻觉率。
- 根据点击、收藏、详情访问和优惠券转化调整排序权重。

## 17. 关键指标

### 17.1 产品指标

- Agent 会话启动率。
- 用户问题一次解决率。
- 连续追问完成率。
- 推荐卡片点击率。
- 商户详情访问率。
- 优惠券查看率和领取转化率。
- 无结果率。
- 用户主动转回普通搜索的比例。

### 17.2 质量指标

- 意图识别准确率。
- 工具参数正确率。
- 结构化字段真实性。
- 推荐结果满足硬约束的比例。
- 推荐理由可追溯率。
- 越权和敏感信息泄露次数。

### 17.3 成本和稳定性指标

- 单会话平均 Token 消耗。
- 模型调用成功率。
- 首 Token 延迟和总耗时。
- 工具调用错误率。
- 降级率。
- 单用户日均调用次数。

## 18. 测试与验收标准

### 18.1 评测集

准备至少 50 条真实问题，覆盖：

- 预算、距离、品类和营业时间组合。
- 有优惠券和无优惠券场景。
- 连续追问和条件修改。
- 无结果和模糊表达。
- 未登录、登录和用户私有数据。
- 恶意提示词和超长输入。
- 模型超时、Redis 异常和工具失败。

### 18.2 MVP 验收

1. 用户能用自然语言搜索商户。
2. Agent 能正确提取预算、位置、品类和时间。
3. 返回商户必须来自真实业务数据，不虚构商户。
4. 距离、价格、营业状态和优惠券状态由代码校验。
5. 支持至少 3 轮连续追问。
6. 返回文本和结构化商户卡片。
7. 模型异常时能返回普通搜索结果。
8. 用户不能查看其他用户的订单或隐私数据。
9. 每次请求有 traceId 和工具调用日志。
10. 未经确认不执行购买、订阅和订单操作。

## 19. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 模型编造商户或价格 | 用户信任受损 | 只允许引用工具返回字段，结构化数据二次校验 |
| 工具调用链过长 | 延迟和成本增加 | 限制工具次数，先硬过滤再做内容增强 |
| 模型服务不可用 | 对话不可用 | 关键词解析和普通搜索降级 |
| 用户评论提示词注入 | 权限或行为异常 | 不可信内容与系统指令隔离，工具权限代码控制 |
| 推荐不符合用户预期 | 点击和转化下降 | 记录反馈，展示推荐依据，持续建设评测集 |
| 会话上下文膨胀 | 成本和延迟上升 | 消息截断、摘要和 TTL |
| 实时库存变化 | 推荐结果过期 | 展示查询时间，进入购买链路时再次校验 |

## 20. MVP 结论

智能导购 Agent 的第一版应聚焦一个闭环：

```text
自然语言找店
  -> 多条件筛选
  -> 结合附近、营业时间和优惠券
  -> 返回可解释的商户卡片
  -> 支持连续追问
  -> 异常时降级为普通搜索
```

该范围能够最大化复用现有的商户、Redis GEO、优惠券、博客、用户和可观测能力，同时控制模型成本、业务风险和开发复杂度，为后续的个性化推荐和优惠券订阅打下基础。
