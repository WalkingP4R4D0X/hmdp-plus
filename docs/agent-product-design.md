# 黑马点评智能导购 Agent 产品设计

## 1. 项目定位

本项目为黑马点评增加一个自然语言找店入口。用户用一句话描述位置、品类、预算或消费场景，Agent 查询现有商户与优惠券数据，返回可跳转的商户卡片和简短推荐理由。

这是一个面向校招展示的 Agent MVP：重点是把大模型接入真实业务数据，并用代码约束模型，而不是实现通用聊天机器人或完整推荐系统。

## 2. MVP 范围

### 要实现

- 自然语言查询商户：识别品类、关键词、预算、距离、评分、营业时间、场景和优惠券需求。
- 根据用户定位查询附近商户；没有定位时提示用户补充位置或按关键词搜索。
- 查询商户、附近商户、优惠券和内容摘要等只读信息。
- 支持连续追问，例如“预算改成 100 元以内”。
- 返回文本、结构化商户卡片和筛选条件。
- 支持流式输出；模型不可用时降级为普通关键词搜索。

### 暂不实现

- 领券、秒杀、下单、订阅提醒等写操作。
- 自动学习用户画像、向量数据库、复杂推荐模型。
- 多 Agent 协作、工作流编排平台和独立 Agent 微服务。
- 灰度发布、Kafka 异步链路和生产级监控告警。

## 3. 设计原则

1. **真实数据优先**：商户、价格、距离、营业状态和优惠券信息只取自业务查询结果。
2. **模型理解，代码决策**：模型把自然语言转换为筛选条件，并生成说明；筛选、排序和卡片字段由 Java 完成。
3. **只读与最小权限**：MVP 只注册查询工具；用户身份从登录上下文获取，不能由模型传入。
4. **可解释、可降级**：推荐理由引用实际字段；模型失败时明确提示已切换到普通搜索。
5. **范围可控**：一次最多返回 10 家商户，优先展示 3–5 家。

## 4. 典型场景

### 自然语言找店

> 拱墅区有没有人均 100 元以内、适合约会的餐厅？

系统解析区域、预算和场景，使用真实商户数据筛选并排序。

### 附近商户

> 找距离我 3 公里内、晚上 9 点还营业的火锅店。

系统从请求上下文读取定位，用 Redis GEO 查询候选商户，再按距离和营业时间过滤。

### 连续追问

```text
用户：推荐几家适合朋友聚餐的店
用户：预算控制在每人 100 元以内
用户：哪家有优惠券？
```

会话保存最近消息和当前筛选条件；后续提问只更新用户明确修改的字段。

## 5. 用户流程

```text
输入问题
  -> 解析结构化条件
  -> 查询商户/附近商户/优惠券
  -> Java 过滤与排序
  -> 生成推荐说明
  -> 展示文本与商户卡片
  -> 继续追问或进入商户详情
```

无结果时，返回已经生效的筛选条件，并建议用户放宽距离、预算或营业时间。模型、Redis 或工具查询异常时，返回普通搜索结果或明确错误，不伪装成推荐成功。

## 6. 功能需求

| 编号 | 功能 | 优先级 |
| --- | --- | --- |
| F-01 | 自然语言输入与商户推荐 | P0 |
| F-02 | 预算、距离、品类、评分和营业时间解析 | P0 |
| F-03 | 商户卡片与现有详情页跳转 | P0 |
| F-04 | Redis 多轮上下文和条件修改 | P0 |
| F-05 | 模型失败降级为普通搜索 | P0 |
| F-06 | SSE 流式展示、停止生成 | P1 |
| F-07 | 优惠券与内容摘要增强 | P1 |
| F-08 | 用户偏好和复杂场景标签 | P2 |

结构化条件示例：

```json
{
  "keyword": "日料",
  "location": "拱墅区",
  "radiusMeter": 3000,
  "budgetMax": 100,
  "minScore": 4.5,
  "openAt": "21:00",
  "scene": "约会",
  "needVoucher": true
}
```

无法可靠识别的字段保留为空，不能由模型猜测。对“附近”“便宜”等模糊表达使用代码中定义的默认值，并在响应的 `filters` 中返回。

## 7. 结果展示

每个商户卡片至少包含：商户 ID、名称、地址、距离、评分、人均价格、营业状态、优惠券摘要和推荐理由。卡片中的结构化字段只能来自本次查询结果；缺失数据展示“信息缺失”，不得编造。

前端页面包含消息列表、输入框、停止按钮和商户卡片。点击卡片复用现有商户详情、博客和优惠券页面，不重复实现业务详情。

## 8. 接口约定

```text
POST   /agent/chat
POST   /agent/chat/stream
GET    /agent/conversations/{conversationId}/messages
DELETE /agent/conversations/{conversationId}
```

请求核心字段为 `conversationId`、`message` 和 `clientRequestId`。响应包含 `conversationId`、`answer`、`cards`、`filters`、`fallback` 和 `traceId`。

流式接口按 `status`、`filter_update`、`shop_card`、`text_delta`、`fallback/error`、`done` 的顺序发送事件；每个事件带递增 `seq`，前端据此去重。

## 9. 验收与展示

项目演示至少覆盖以下场景：

1. 一句话按品类、预算和位置找到真实商户。
2. 附近查询正确处理“无定位”“无结果”和 Redis 不可用。
3. 连续三轮修改条件，旧条件能正确保留或被覆盖。
4. 结果满足预算、距离、营业时间等硬约束。
5. SSE 能逐步展示回答；停止后不再追加内容。
6. LLM 超时或返回非法结果时切换到普通搜索。
7. 未登录用户不能读取其他用户的偏好或私有数据。

## 10. 面试表达重点

可以围绕以下闭环介绍项目：**LLM 结构化解析 -> 受控工具查询 -> 代码校验与排序 -> 流式卡片返回 -> 异常降级**。重点说明为何不让模型直接访问数据库，以及如何避免模型编造商户、价格和优惠券信息。
